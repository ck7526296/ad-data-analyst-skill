# 贡献与同步流程

本文件用于用户要求完善 Skill、生成补丁、同步源码仓库或创建 GitHub PR 的场景。

## 默认原则

- 默认只生成规则变更单、补丁和审查报告，不直接提交 PR。
- 当前安装目录可能不是 Git 仓库，不能假设 `/Users/ck/.codex/skills/ad-data-analyst` 可以直接提交。
- GitHub 同步必须由用户明确要求，并且存在可提交的 Skill 源码仓库。
- 规则文件不保存账号、token、Authorization、客户敏感信息、后台权限或合同价格。

## 规则变更单

每次用户提出规则修改时，先整理：

```markdown
## 规则变更单
- 修改类型: 项目规则 / 分析规则 / 输出规则
- 触发问题: 用户原始反馈
- 当前问题: 现有 Skill 为什么答得不理想
- 新规则: 具体新增或调整的规则
- 适用范围: 全局 / 项目级 / 问题类型 / 输出模板
- 涉及文件: references/project-rules.md / analysis-rules.md / output-rules.md / SKILL.md
- 验证用例: 至少 1 个用户问题和期望输出特征
- 风险: 可能误用、过期或和 MCP 数据冲突的点
```

## 生成补丁

没有上游仓库、用户未授权 PR 或 GitHub 权限不明时，输出：

1. 规则变更单
2. 建议 diff 或 patch
3. 验证问题
4. 回滚方式

补丁应尽量只改 `references/` 中对应规则文件；只有新增规则入口、导航或触发说明时才改 `SKILL.md`。

## GitHub 同步

用户明确要求同步到仓库或 GitHub 时：

1. 确认源码仓库路径，不把安装目录当源码仓库。
2. 检查该路径是否为 Git 仓库、是否有 remote、当前分支和工作区状态。
3. 若工作区有无关改动，先说明并避免覆盖。
4. 创建分支：`codex/update-ad-data-rules-*`。
5. 应用补丁到源码仓库。
6. 提交 commit，提交信息说明规则类型和适用范围。
7. 推送分支。
8. 创建 GitHub PR。

PR 描述必须包含：规则变更单、验证用例、风险、回滚方式。若任一步失败，停止同步并输出失败原因和已完成步骤。

## 审查清单

- 规则是否有明确适用范围。
- 项目规则是否包含 `productCode` 和生效日期。
- 输出规则是否区分一次性要求和长期偏好。
- 分析规则是否仍以 MCP 数据、ROI、转化成本和设备/回传质量为核心。
- 是否避免把 sent、可能结算设备、回传率、扣量比例当作 ROI。
- 是否避免保存敏感信息。
